# 电商商品文案生成系统 — 架构设计

## 0. 一句话概述

一个从**数据标注 → 模型微调 → 质量评估 → 推理部署**的完整 LLM 微调管线。核心理念：**每个环节都可独立验证，每项决策都有数据支撑**。

---

## 1. 硬件与模型双轨策略

**本地训练环境**：RTX 5070 Ti Laptop 12GB GDDR7

| 轨道 | 模型 | 硬件 | 场景 |
|------|------|------|------|
| **本地轨道** | Qwen3-14B Dense | 5070 Ti 12GB | 日常开发、快速迭代、消融实验 |
| **云端轨道** | Qwen3.5-35B-A3B MoE | A100/H100 40GB+ | 最终模型、GRPO对齐、Judge评估 |

**设计理由**：
- Qwen3-14B QLoRA 4-bit 仅需 ~8-11GB，刚好塞进 12GB 显存，batch_size=4 可跑
- 35B-A3B MoE 虽然激活参数仅 3B，但 35B 全量参数 4-bit 量化后仍需 ~17.5GB，超出 12GB
- 本地用 14B 快速验证想法，云端用 35B-MoE 出最终模型，训练代码完全复用，只换模型路径
- 面试时这是一个加分项：展示了对硬件约束下工程决策的理解

**显存估算**：

| 模型 | 全量 FP16 | QLoRA 4-bit | 5070 Ti 12GB |
|------|----------|-------------|-------------|
| Qwen3-8B | 16GB | ~5-7GB | ✅ 宽裕 |
| Qwen3-14B | 28GB | ~8-11GB | ✅ 刚好 |
| Qwen3.5-35B-A3B | 70GB | ~17.5GB | ❌ 超了 |
| Qwen3.5-2B | 4GB | ~1.5GB | ✅ 太宽裕，太小 |

## 3. 数据层：标注管线

### 2.1 数据流

```
原始商品数据 (JSON)
    │
    ├── [品类] 3C数码 / 美妆 / 家居 / 食品
    ├── [字段] title, category, brand, price, features, target_audience, existing_desc
    │
    ▼
┌─────────────────────────────────────────────────────┐
│ 步骤1: LLM 预标注                                     │
│                                                      │
│ 输入: 商品属性JSON                                     │
│ 模型: Qwen3-14B-Instruct (本地) / Qwen3.5-35B-A3B (云端)   │
│ Prompt: 按模板生成初版文案                               │
│ 输出: { "raw_copy": "...", "confidence": 0.85 }      │
│                                                      │
│ 目的: 承担70%工作量，人工只需修正而非从零写               │
└─────────────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────────────┐
│ 步骤2: 人工精标 (Label Studio)                        │
│                                                      │
│ 标注界面: 左右分栏                                     │
│   左侧: 商品属性 + LLM预标注结果                        │
│   右侧: 人工编辑区                                     │
│                                                      │
│ 操作:                                                │
│   - 修正事实错误（属性值写错）                           │
│   - 补充遗漏卖点（LLM没提到的关键feature）              │
│   - 提升语言质量（不流畅/不吸引人）                      │
│   - 标注合规标签（违禁词/虚假宣传）                      │
│                                                      │
│ 标注结构:                                             │
│   {                                                  │
│     "final_copy": "人工修正后的最终文案",               │
│     "edited": true/false,                            │
│     "edit_type": ["fact_fix", "sell_point_add", ...], │
│     "quality_label": "good" | "acceptable" | "poor"  │
│   }                                                  │
└─────────────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────────────┐
│ 步骤3: IAA 一致性校验                                  │
│                                                      │
│ 双标注员: 同一商品由两位标注员独立标注                    │
│ 指标: Cohen's Kappa (分类) / Krippendorff's Alpha    │
│ 阈值: Kappa ≥ 0.85                                   │
│ 仲裁: 低于阈值 → 第三位标注员仲裁                       │
│                                                      │
│ 代码: annotation/iaa_check.py                        │
│   输入: 两位标注员的标注结果                             │
│   输出: Kappa值 + 不一致样本列表 + 仲裁建议              │
└─────────────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────────────┐
│ 步骤4: 主动学习 (可选)                                 │
│                                                      │
│ 策略: 训练基线模型 → 推理全部未标注数据                  │
│       → 选取模型困惑度最高的样本 (perplexity top-k)     │
│       → 优先标注这些样本                                │
│                                                      │
│ 代码: annotation/active_learning.py                   │
│   输入: 未标注数据 + 基线模型                           │
│   输出: 优先标注的样本ID列表 (sorted by perplexity)     │
└─────────────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────────────┐
│ 最终输出: Alpaca格式数据集                             │
│                                                      │
│ {                                                    │
│   "instruction": "你是一名专业的电商文案撰写师...",     │
│   "input": "{商品属性JSON}",                          │
│   "output": "高质量文案",                              │
│   "metadata": {                                      │
│     "category": "3C数码",                            │
│     "quality_label": "good",                         │
│     "edit_count": 2,                                 │
│     "annotator_id": "A01"                            │
│   }                                                  │
│ }                                                    │
│                                                      │
│ 规模: train_2000.json / val_200.json / test_200.json │
└─────────────────────────────────────────────────────┘
```

### 3.3 GRPO 对齐 (Phase 3, 可选)

```
GRPO (Group Relative Policy Optimization) 流程:

1. 采样阶段
   Policy Model ──→ 对同一商品生成 K 条文案 (K=4)
   
2. 评分阶段
   Reward Model (LLM-as-Judge) ──→ 对每条文案四维评分
   
3. 对比阶段
   组内归一化: Advantage = (score_i - mean_group) / std_group
   
4. 更新阶段
   用 Advantage 加权更新 Policy, 约束 KL 散度
   
优势 vs DPO:
  - 在线采样: 用当前模型生成样本，不是离线偏好对
  - 组内归一化: 消除绝对分值波动
  - 避免 Reward Hacking: KL 约束防止模型骗分
```

## 5. 评估层：LLM-as-Judge

### 4.1 评估流程

```
微调模型推理 (test_200.json)
    │
    ▼
┌─────────────────────────────────────────────────────┐
│  Step 1: 模型推理                                     │
│                                                      │
│  Base Model (Qwen3-14B / Qwen3.5-35B-A3B MoE) + LoRA   │
│    → 对 test_200 的每条数据生成文案                     │
│    → 保存 {id, input, generated, reference}           │
└─────────────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────────────┐
│  Step 2: LLM-as-Judge 四维评分                        │
│                                                      │
│  Judge 模型: Qwen3-32B-Instruct (或 API)              │
│                                                      │
│  评分维度:                                             │
│  ┌──────────────┬──────────────────────────────────┐ │
│  │ 维度          │ 评估标准                          │ │
│  ├──────────────┼──────────────────────────────────┤ │
│  │ 准确性(0-10)  │ 属性值、规格、品牌是否与原文一致    │ │
│  │ 吸引力(0-10)  │ 语言流畅度、卖点突显、购买欲望      │ │
│  │ 合规性(0-10)  │ 广告法、虚假宣传、违禁词           │ │
│  │ SEO(0-10)     │ 关键词密度、标题结构、搜索友好      │ │
│  └──────────────┴──────────────────────────────────┘ │
│                                                      │
│  输出: { accuracy: {score, reason}, ... overall }     │
│                                                      │
│  文件: evaluation/llm_judge.py                        │
└─────────────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────────────┐
│  Step 3: 自动指标计算                                  │
│                                                      │
│  指标              计算方式             目标           │
│  ──────────────────────────────────────────────────  │
│  事实错误率        属性值≠原文属性       < 5%           │
│  幻觉率            生成原文不存在的属性   < 3%           │
│  合规违规率        命中违禁词列表        < 1%           │
│  BLEU-4            n-gram重叠          > 0.25         │
│  ROUGE-L           LCS匹配             > 0.40         │
│  Judge-Accuracy    Judge准确性评分       > 7.0          │
│  Judge-Attract     Judge吸引力评分       > 7.0          │
│  Judge-Compliance  Judge合规评分         > 8.0          │
│  Judge-SEO         Judge SEO评分         > 7.0          │
│                                                      │
│  文件: evaluation/auto_metrics.py                     │
└─────────────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────────────┐
│  Step 4: Judge 校准                                   │
│                                                      │
│  - 随机抽取100条文案                                    │
│  - 3位标注员独立评分 → Ground Truth (均值)              │
│  - 计算 Spearman ρ (Judge vs Human)                  │
│  - ρ ≥ 0.80 → 通过                                    │
│  - ρ < 0.80 → 调整 Judge Prompt / 换模型              │
│  - 分维度检查偏差（是否有系统性高估/低估）                 │
│                                                      │
│  文件: evaluation/judge_calibration.py                │
└─────────────────────────────────────────────────────┘
    │
    ▼
  评估报告 (outputs/eval_reports/report_v1.json)
```

### 4.2 Judge Prompt 设计

```
Judge Prompt 设计原则:
1. 角色设定: "资深电商文案评审专家" → 锚定评审标准
2. 结构化输出: 强制 JSON → 可解析、可对比
3. 评分锚点: 0-10分，每个分数有描述 → 减少尺度漂移
4. 强制理由: 每个维度必须给出 reason → 可审计、可调试
5. 参考原文: 提供商品属性原文 → 检查准确性
6. 负面清单: 明确列举违禁行为 → 约束合规评分
```

## 8. 消融实验设计

### 7.1 为什么要做消融实验

面试中回答"为什么选这个参数"时，需要有数据支撑：
- "LoRA rank=16 而不是 8 或 32，因为 rank=16 时 Judge 总分最高，rank=8 欠拟合，rank=32 过拟合"
- "数据量从 1000 到 2000 提升 12%，但 2000 到 3000 只有 3%，边际递减明显"
- "学习率 1e-3 导致训练不稳定，eval_loss 波动大；2e-4 是最优的"

### 7.2 实验优先级

```
P0 (必做, 证明基本能力):
  - Baseline: rank=16, data=2000, lr=2e-4, target=all, SFT
  - 数据量消融: 500/1000/2000/3000

P1 (加分, 展示深度):
  - LoRA rank消融: 8/16/32/64
  - 学习率消融: 1e-4/2e-4/5e-4/1e-3

P2 (亮点, 锦上添花):
  - LoRA target消融: qv_only/qkvo/all
  - 多任务 vs 单任务
  - SFT vs SFT+GRPO

P3 (可选):
  - 不同基座模型对比 (Qwen3.5-MoE vs Qwen3.5-2B-Dense)
  - MoE vs Dense 架构对比分析
  - 不同微调框架对比 (LLaMA-Factory vs Unsloth)
```

### 7.3 消融实验脚本设计

```bash
# training/ablation/run_ablation.sh
# 核心思路: 用脚本循环配置，每次训练→评估→记录

# 数据量消融
for size in 500 1000 2000 3000; do
    # 1. 准备数据子集
    python prepare_subset.py --size $size
    
    # 2. 训练
    llamafactory-cli train config.yaml \
        --dataset ecommerce_${size} \
        --output_dir outputs/lora_ablation/data_${size}
    
    # 3. 评估
    python ../evaluation/llm_judge.py \
        --adapter outputs/lora_ablation/data_${size} \
        --test_data data/test/test_200.json \
        --output outputs/eval_reports/ablation_data_${size}.json
    
    # 4. 记录到MLflow
    python log_to_mlflow.py \
        --experiment "data_size_ablation" \
        --run_name "size_${size}" \
        --eval_report outputs/eval_reports/ablation_data_${size}.json
done
```
